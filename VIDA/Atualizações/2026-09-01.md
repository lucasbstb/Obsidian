## 1. O que o sistema é

Plataforma de vigilância de sinistros de trânsito do CET-Rio. Consolida acidentes
de várias fontes, georreferencia, qualifica (revisão, duplicidades, imprecisos) e
entrega mapa, painéis OMS e exportação para o DETRAN.

O mapa completo ficou em [[Arquitetura e mapa do sistema]]. Três descobertas
merecem destaque.

### O banco é Django, não TypeORM

`auth_user`, `incident_trafficincident`, colunas `traffic_incident_id_id`. O
schema nasceu de uma aplicação Django e o NestJS foi construído por cima. É a
explicação para os scripts Python existirem: são legado daquela era, nunca
migrados.

E explica o `synchronize: false` **sem migrations no repositório** — o schema só
existe no servidor. Não há como reconstruir o banco a partir do git.

### O sistema nasceu em Fortaleza

```
pefoce_code   = Perícia Forense do Estado do CEARÁ
amc_code      = Autarquia Municipal de Trânsito (Fortaleza)
get-coordinates-from-google.ts:  ', Fortaleza, CE, Brasil'   ← fixo no código
```

> **Risco vivo:** qualquer endereço geocodificado pela API cai no Ceará. Não
> afeta a importação do ISP (a planilha traz `geom` pronto), mas afeta o
> cadastro manual pela tela.

### Só duas das seis fontes passam pela API

`samu_code` e `prf_code` têm importador em TypeScript. `amc_code`, `pre_code`,
`pefoce_code` e `sim_code` aparecem **só na exportação** — nenhuma linha do
projeto grava neles.

Foi essa lacuna que levou ao pipeline Python. As fontes do Rio são **CBMERJ** e
**ISP**, e ambas entram por script solto na Desktop de uma workstation.

## 2. O mito do espelho

A informação recebida era: *"o banco do Proxmox lê o que está na máquina do
CET"*. Investiguei as quatro hipóteses — replicação física, lógica, FDW e cópia
por cron.

**Nenhuma existe.** Zero configuração de replicação em qualquer lugar.

A explicação apareceu no `.env`, num bloco comentado que estava lá desde sempre:

```env
#HOMOLOG DB
# DB_HOST=10.39.64.110
```

E o script Python confirmou, com `DB_HOST = "localhost"`: ele grava no banco da
própria máquina do CET.

> O "espelho" era o dev anterior **trocando uma linha do `.env`** para apontar a
> *aplicação* ao banco do CET quando queria os dados reais. Telefone sem fio.

O que existe de fato é cópia manual, encontrada no histórico do PowerShell dele:

```powershell
docker cp db-vida:/tmp/backup_27_10_2025.dump  C:\...\db-postgres\
docker cp C:\...\backup_27_10_2025.dump  db-vida-cet-dev:/tmp/
docker run -d -p 5433:5432 --name db-vida-cet-dev db-vida-cet
```

`db-vida-cet-dev` é uma cópia restaurada do `db-vida`, feita à mão em 27/10/2025.

## 3. Os IPs mentiam

O `nginx.conf` aponta para `10.29.0.161`. Passei um bom tempo tentando conectar
o DBeaver por túnel SSH nesse IP e recebendo `password authentication failed` —
com a credencial certa.

```bash
hostname -I
10.29.0.167  172.17.0.1  172.18.0.1  172.19.0.1
```

**A VM é `.167`.** O `.161` é outra máquina viva na mesma sub-rede, que aceitou
o SSH com a mesma senha de root e tem *um outro* Postgres em `localhost:5432` —
daí o erro de senha.

Ou o IP da VM mudou e o nginx nunca foi atualizado, ou existe um segundo
ambiente que ninguém mapeou. **Em aberto.**

## 4. A rede do CET é intransponível

```
nc -z -w 3 -v 10.39.64.110 5432   → timeout
nc -z -w 3 -v 10.39.64.110 3389   → timeout   ← nem o RDP
tracepath -m 8 10.39.64.110       → atravessa 8 hops do backbone 172.16.x
```

O tráfego **é roteado** — sai da VLAN, percorre o backbone da Prefeitura — e o
firewall descarta na chegada. Como nem a 3389 passa, não é filtro de porta: é
bloqueio de todo TCP daquela origem.

Testado das duas máquinas, com o mesmo resultado. Não é ajustável do nosso lado.

> O `ping` retornando `Redirect Host (New nexthop: 10.29.0.33)` com 100% de perda
> me levou a uma hipótese errada de rota faltando. O `tracepath` desmentiu: ICMP
> echo é só filtrado por política, o que é normal.

Sobrou o RDP — onde o **copiar e colar está bloqueado**. Todo comando na máquina
do CET é digitado à mão.

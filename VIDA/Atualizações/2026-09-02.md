## 1. O lock de quinze horas

```
 pid | state               | query                                    | xact_start
-----+---------------------+------------------------------------------+--------------------
 391 | idle in transaction | select (select count(*) from incident_tr  | 2026-09-01 16:28:20
 876 | active              | INSERT INTO incident_trafficincident (ne | 2026-09-01 20:20:27
```

A PID 391 é a sessão onde rodei `BEGIN; TRUNCATE ...` e a consulta de
conferência. **O `COMMIT` nunca foi digitado.** O `TRUNCATE` segurava lock
`ACCESS EXCLUSIVE` desde as 16:28.

Às 20:20 o script entrou na fila. E ficou.

> **Matar o processo Python não resolve.** O backend do Postgres continua
> esperando o lock — o cliente ter morrido só é percebido quando a query termina.
> Foi preciso `pg_terminate_backend` nos dois.

Ao matar a 391, o rollback devolveu os 31.069 sinistros. O banco voltou
exatamente ao estado da véspera, o que pelo menos deu uma prova de que a
transação estava mesmo intacta.

### A regra que fica

Comando único vai pela forma não interativa, que faz autocommit e fecha a sessão
sozinha:

```powershell
docker exec <container> psql -U admin -d <banco> -c "COMANDO"
```

E um `TRUNCATE` já é atômico por natureza — o `BEGIN` não protegia nada que ele
não protegesse sozinho. Só criou a chance de esquecer o `COMMIT`.

> Detalhe traiçoeiro: com `-c`, um `BEGIN` **sem** `COMMIT` na mesma string faz o
> psql dar rollback ao sair. O comando é desfeito e nada avisa.

O prompt do psql avisa o tempo todo, e eu não estava olhando:
`vidadev=#` normal, `vidadev=*#` transação aberta, `vidadev=!#` abortada.

## 3. O `NaN` que virava texto

```
event              | NaN
textual_reference  | NaN
```

Célula vazia na planilha vira `NaN` no pandas, e o script gravava **a string
literal "NaN"** no banco. Não é `NULL`: `WHERE campo IS NULL` deixa de achar, o
export imprime "NaN" e a tela mostra isso ao usuário.

Em 31 mil registros, viraria sujeira difícil de limpar.

A correção é uma linha — e curiosamente o `criacao_registros_cbrj.py` já a
tinha, enquanto o `migracao.py` não:

```python
df = df.where(pd.notna(df), None)
```

Vale para **todos** os blocos de uma vez. Testado: os dois campos agora vêm
vazios, e o `geom` continua preenchido.

## Duas coisas que os dados obrigaram a mudar

**O bairro precisou de normalização, não de comparação crua.** O ISP grava
`MARE`, a COR grava `Maré`:

| Fonte | Grafia | Registros |
|---|---|---|
| ISP | `MARE`, `IRAJA`, `GALEAO`, `SAO CRISTOVAO` | maiúscula, sem acento |
| COR | `Maré`, `Irajá`, `Galeão`, `São Cristóvão` | title case, com acento |

Comparação crua reprovaria **3.247 dos 11.180 registros da COR (29%)** só por
isso. Normalizando, sobram 141 (1,3%) — e o que sobra é diferença real
(`FREGUESIA JACAREPAGUA`, `EXTERNO`, células com `.`).

**A dedup não podia ser hash de conteúdo como no CBMRJ.** A planilha da COR traz
a mesma ocorrência em estágios diferentes — o conteúdo muda, o hash não pega. A
chave é o `Id_ocorrencia`, que é o que o slide chama de "deixar apenas o último
registro". Evidência: **50 `cor_code` repetidos** no banco de dev.

**De brinde:** o `Id_ocorrencia` vinha com o literal `_x000D_` e quebra de linha
do Excel indo direto para o `cor_code`. Novo utilitário `cleanCellValue`.

## ⚠️ O que a medição de impacto revelou — decisão pendente

## A geografia, no escopo que os slides pedem

Os slides **não** têm geografia entre os critérios de match — só Time ±3h, nome
de via e nome do bairro. Ela aparece condicionando duas entradas do dicionário:
"exigir coordenada ou segmento" (Transolímpica) e "exigir validação espacial"
(Autoestrada Grajaú).

Foi implementado só isso: a identidade condicionada só se aplica com as duas
coordenadas presentes e a menos de 500 m. **Sem trava geográfica geral** — não
está no documento.

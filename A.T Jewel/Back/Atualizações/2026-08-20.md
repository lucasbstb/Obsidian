## O 409 que barrava gente de verdade

O integrador mandou o print:

```
statusCode: 409
message: "Ja existe cliente com esse telefone (id: b8c583da-...)"
   at CriarClienteUseCase.execute (/app/src/.../criar-cliente.use-case.ts:85:17)
```

Não era duplicata. Era **gente diferente com o mesmo número** — mãe e filha,
marido e mulher, o fixo da empresa no cadastro do dono, o telefone da loja
digitado como placeholder. O ERP tem vários assim, e cada um deles ficava **de
fora do CRM**: a criação falhava e o registro nunca entrava.

A pergunta certa não era *"tira a chave?"*, era **qual campo é identidade**:

| Campo | Identidade? | Continua único? |
|---|---|---|
| `id_erp`, `codigo_erp` | sim — quem o cliente é no Safira | sim |
| `clientes_perfil.whatsapp_hash` | sim — o canal | **sim** |
| `clientes.telefone_1` | não — dado de contato | não |
| `clientes.email` | não — mesmo caso | não |

O `whatsapp_hash` fica único **de propósito**, e a diferença é o ponto todo: uma
mensagem que chega precisa resolver para UM cliente, senão o roteamento da
Anastasia não tem como decidir com quem está falando. Ali a unicidade é o que faz
o mecanismo funcionar. No cadastro do ERP ela só barrava gente legítima.

Migração 36 tira o `UNIQUE` de `telefone_1_hash` e `email_hash` e **mantém os
índices** — eles são o caminho de busca, não têm a ver com unicidade.

### O que a trava protegia, e não protegia

O comentário no código dizia que ela existia para o mesmo número não entrar em
dois formatos e partir o histórico em dois. Só que **a Anastasia nunca
deduplicou por `telefone_1_hash`** — ela deduplica por `whatsapp_hash`, em
`BuscarClientePorWhatsappUseCase`. A trava nunca cobriu o caso que pretendia
cobrir.

O que ela cobria era outra coisa, por acidente: **reenvio sem chave**. Testado:

```
A) 5 pessoas diferentes, mesmo telefone, cada uma com seu id_erp
   201 201 201 201 201        todas entram

B) o mesmo cliente reenviado 3x COM id_erp
   201, 409, 409              idempotente

C) o mesmo cliente reenviado 3x SEM id_erp e SEM codigoErp
   201, 201, 201              TRÊS clientes iguais, em silêncio
```

O caso C passou a depender **inteiramente** do integrador mandar
`idErpCliente`. A doc foi atualizada com isso em destaque. Ficou **em aberto**
(decisão do Lucas) exigir o campo quando a chamada vem por API key — vale
retomar se o cadastro sujar.

## Uma checagem que estava prometida em comentário e nunca foi escrita

A contraprova de que o WhatsApp continua barrando devolveu isto:

```
HTTP 500  duplicate key value violates unique constraint
          "clientes_perfil_whatsapp_hash_key"
```

E o código dizia, desde o início:

```ts
// Idempotencia: se ja existe cliente com esse whatsapp_hash, conflito.
const telefone1Hash = input.telefone1   // ← o comentario ficou orfao uma linha acima
```

A mão escorregou uma linha na época e ninguém percebeu, porque **o 500 só
aparece para quem tenta duplicar** — e até hoje ninguém tinha tentado. Duplicata
de WhatsApp sempre voltou como violação crua do Postgres: nome de tabela e de
constraint entregues a quem chamou, sem dizer qual é o registro.

Agora é `409` com o `id` do existente, cobrindo as variantes do número (nono
dígito, DDI) pelo mesmo motivo do lookup.

Vale registrar o padrão: **foi a remoção de uma trava que revelou a outra**.
Enquanto o telefone barrava, quase nada chegava ao ponto de testar o WhatsApp.

## O deploy

Seis commits de uma vez — o ciclo inteiro do encaminhamento de ontem mais a
migração 36. Merge `lucasdevback` → `main` em fast-forward, `0b9ea70..d7c3995`.

**Não era o `git pull` + restart de sempre**, e três coisas mudaram o
procedimento:

```bash
git pull origin main
docker exec atjewel_api npm install               # @nestjs/schedule é novo
docker exec -it atjewel_api npm run db:migrate    # 35 e 36 — o -it é obrigatório
docker restart atjewel_api
```

1. **`@nestjs/schedule` entrou no `package.json`.** Como `/app/node_modules` é
   volume, o pull não traz o pacote. Sem o `npm install` dentro do contêiner a
   API não sobe: `Cannot find module`.
2. **O `migrate.js` aborta sem TTY, de propósito** — sem `-it` não há como
   confirmar, e rodar direto seria exatamente o que a barreira existe para
   impedir. Ele mostrou `[PRODUCAO]` e cobrou a palavra: o marcador
   `AMBIENTE=producao` está mesmo no `.env` do servidor.
3. **Migrar ANTES de reiniciar.** Se a API subisse com o código novo e as tabelas
   ainda não existissem, o cron passaria a varrer de minuto em minuto uma tabela
   inexistente.

Subiu limpo — `ScheduleModule`, `AtendimentosModule`, `LlmModule` e
`WhatsappGatewayModule` inicializados, nenhuma dependência circular. E o log
ficou em silêncio depois, que é o resultado certo: a tabela nasceu vazia.

Efeito colateral bom: **o webhook adormecido saiu do ar.** A `main` registrava o
`ProcessarMensagemWhatsappUseCase` no `/whatsapp/webhook` — ele processava e
**respondia**, com a persona errada, para quem chamasse a URL com o token. Agora
a rota é o canal interno com default-deny.

### O que está no ar, e o que ainda não

O fluxo de atendimento subiu **dormente**. Ele só funciona quando alguma
vendedora tiver `whatsapp_interno` preenchido em produção — hoje **nenhuma tem**,
o número só existe no local. O que subiu é a máquina, pronta para o chip interno.

## Achado de segurança, adiado com nome e endereço

O stack trace no print do integrador **não deveria estar ali**. O filtro está
certo — só inclui o stack fora de produção. O problema é que o servidor não está
como produção:

```yaml
# docker-compose.yml
environment:
  NODE_ENV: development     # e o `environment:` GANHA do env_file
```

Mexer só no `.env` do servidor não resolve nada.

| | O que acontece hoje em produção |
|---|---|
| 1 | **5xx devolve a mensagem crua do banco** — nome de tabela e de constraint |
| 2 | Stack trace em toda resposta de erro |
| 3 | TypeORM com `logging: true` — **toda query** no log, com parâmetros |
| 4 | Log em formato dev em vez de JSON |

**A correção não é trocar `NODE_ENV`.** O `scripts/migrate.js` já bateu nessa
parede e resolveu de outro jeito, e está escrito lá:

> *"E `NODE_ENV` nao ajuda: o compose fixa `development` nos dois ambientes. Por
> isso o criterio e um marcador explicito no `.env`: `AMBIENTE=producao`"*

Usar o mesmo marcador no filtro de erros e no logging mexe só no que a gente quer
mexer. Trocar o `NODE_ENV` tem **armadilha**: o contêiner roda `nest start
--watch`, que precisa de `@nestjs/cli`, `typescript` e `ts-node` em tempo de
execução — e os três são **devDependencies**. Com `NODE_ENV=production` no
ambiente, qualquer `npm install` rodado dentro do contêiner some com eles e a API
não sobe mais.

Foi sorte de calendário: **se tivéssemos trocado antes**, o `npm install` deste
deploy teria quebrado a API.

Adiado a pedido do Lucas.

## O 409 que barrava gente de verdade

O integrador mandou o print:

```
statusCode: 409
message: "Ja existe cliente com esse telefone (id: b8c583da-...)"
   at CriarClienteUseCase.execute (/app/src/.../criar-cliente.use-case.ts:85:17)
```

Não era duplicata. Era **gente diferente com o mesmo número** — mãe e filha,
marido e mulher, o fixo da empresa no cadastro do dono, o telefone da loja
digitado como placeholder. O ERP tem vários assim, e cada um deles ficava **de
fora do CRM**: a criação falhava e o registro nunca entrava.

A pergunta certa não era *"tira a chave?"*, era **qual campo é identidade**:

| Campo | Identidade? | Continua único? |
|---|---|---|
| `id_erp`, `codigo_erp` | sim — quem o cliente é no Safira | sim |
| `clientes_perfil.whatsapp_hash` | sim — o canal | **sim** |
| `clientes.telefone_1` | não — dado de contato | não |
| `clientes.email` | não — mesmo caso | não |

O `whatsapp_hash` fica único **de propósito**, e a diferença é o ponto todo: uma
mensagem que chega precisa resolver para UM cliente, senão o roteamento da
Anastasia não tem como decidir com quem está falando. Ali a unicidade é o que faz
o mecanismo funcionar. No cadastro do ERP ela só barrava gente legítima.

Migração 36 tira o `UNIQUE` de `telefone_1_hash` e `email_hash` e **mantém os
índices** — eles são o caminho de busca, não têm a ver com unicidade.

### O que a trava protegia, e não protegia

O comentário no código dizia que ela existia para o mesmo número não entrar em
dois formatos e partir o histórico em dois. Só que **a Anastasia nunca
deduplicou por `telefone_1_hash`** — ela deduplica por `whatsapp_hash`, em
`BuscarClientePorWhatsappUseCase`. A trava nunca cobriu o caso que pretendia
cobrir.

O que ela cobria era outra coisa, por acidente: **reenvio sem chave**. Testado:

```
A) 5 pessoas diferentes, mesmo telefone, cada uma com seu id_erp
   201 201 201 201 201        todas entram

B) o mesmo cliente reenviado 3x COM id_erp
   201, 409, 409              idempotente

C) o mesmo cliente reenviado 3x SEM id_erp e SEM codigoErp
   201, 201, 201              TRÊS clientes iguais, em silêncio
```

O caso C passou a depender **inteiramente** do integrador mandar
`idErpCliente`. A doc foi atualizada com isso em destaque. Ficou **em aberto**
(decisão do Lucas) exigir o campo quando a chamada vem por API key — vale
retomar se o cadastro sujar.

## Uma checagem que estava prometida em comentário e nunca foi escrita

A contraprova de que o WhatsApp continua barrando devolveu isto:

```
HTTP 500  duplicate key value violates unique constraint
          "clientes_perfil_whatsapp_hash_key"
```

E o código dizia, desde o início:

```ts
// Idempotencia: se ja existe cliente com esse whatsapp_hash, conflito.
const telefone1Hash = input.telefone1   // ← o comentario ficou orfao uma linha acima
```

A mão escorregou uma linha na época e ninguém percebeu, porque **o 500 só
aparece para quem tenta duplicar** — e até hoje ninguém tinha tentado. Duplicata
de WhatsApp sempre voltou como violação crua do Postgres: nome de tabela e de
constraint entregues a quem chamou, sem dizer qual é o registro.

Agora é `409` com o `id` do existente, cobrindo as variantes do número (nono
dígito, DDI) pelo mesmo motivo do lookup.

Vale registrar o padrão: **foi a remoção de uma trava que revelou a outra**.
Enquanto o telefone barrava, quase nada chegava ao ponto de testar o WhatsApp.

## O deploy

Seis commits de uma vez — o ciclo inteiro do encaminhamento de ontem mais a
migração 36. Merge `lucasdevback` → `main` em fast-forward, `0b9ea70..d7c3995`.

**Não era o `git pull` + restart de sempre**, e três coisas mudaram o
procedimento:

```bash
git pull origin main
docker exec atjewel_api npm install               # @nestjs/schedule é novo
docker exec -it atjewel_api npm run db:migrate    # 35 e 36 — o -it é obrigatório
docker restart atjewel_api
```

1. **`@nestjs/schedule` entrou no `package.json`.** Como `/app/node_modules` é
   volume, o pull não traz o pacote. Sem o `npm install` dentro do contêiner a
   API não sobe: `Cannot find module`.
2. **O `migrate.js` aborta sem TTY, de propósito** — sem `-it` não há como
   confirmar, e rodar direto seria exatamente o que a barreira existe para
   impedir. Ele mostrou `[PRODUCAO]` e cobrou a palavra: o marcador
   `AMBIENTE=producao` está mesmo no `.env` do servidor.
3. **Migrar ANTES de reiniciar.** Se a API subisse com o código novo e as tabelas
   ainda não existissem, o cron passaria a varrer de minuto em minuto uma tabela
   inexistente.

Subiu limpo — `ScheduleModule`, `AtendimentosModule`, `LlmModule` e
`WhatsappGatewayModule` inicializados, nenhuma dependência circular. E o log
ficou em silêncio depois, que é o resultado certo: a tabela nasceu vazia.

Efeito colateral bom: **o webhook adormecido saiu do ar.** A `main` registrava o
`ProcessarMensagemWhatsappUseCase` no `/whatsapp/webhook` — ele processava e
**respondia**, com a persona errada, para quem chamasse a URL com o token. Agora
a rota é o canal interno com default-deny.

### O que está no ar, e o que ainda não

O fluxo de atendimento subiu **dormente**. Ele só funciona quando alguma
vendedora tiver `whatsapp_interno` preenchido em produção — hoje **nenhuma tem**,
o número só existe no local. O que subiu é a máquina, pronta para o chip interno.

## Achado de segurança, adiado com nome e endereço

O stack trace no print do integrador **não deveria estar ali**. O filtro está
certo — só inclui o stack fora de produção. O problema é que o servidor não está
como produção:

```yaml
# docker-compose.yml
environment:
  NODE_ENV: development     # e o `environment:` GANHA do env_file
```

Mexer só no `.env` do servidor não resolve nada.

| | O que acontece hoje em produção |
|---|---|
| 1 | **5xx devolve a mensagem crua do banco** — nome de tabela e de constraint |
| 2 | Stack trace em toda resposta de erro |
| 3 | TypeORM com `logging: true` — **toda query** no log, com parâmetros |
| 4 | Log em formato dev em vez de JSON |

**A correção não é trocar `NODE_ENV`.** O `scripts/migrate.js` já bateu nessa
parede e resolveu de outro jeito, e está escrito lá:

> *"E `NODE_ENV` nao ajuda: o compose fixa `development` nos dois ambientes. Por
> isso o criterio e um marcador explicito no `.env`: `AMBIENTE=producao`"*

Usar o mesmo marcador no filtro de erros e no logging mexe só no que a gente quer
mexer. Trocar o `NODE_ENV` tem **armadilha**: o contêiner roda `nest start
--watch`, que precisa de `@nestjs/cli`, `typescript` e `ts-node` em tempo de
execução — e os três são **devDependencies**. Com `NODE_ENV=production` no
ambiente, qualquer `npm install` rodado dentro do contêiner some com eles e a API
não sobe mais.

Foi sorte de calendário: **se tivéssemos trocado antes**, o `npm install` deste
deploy teria quebrado a API.

Adiado a pedido do Lucas.

## A retomada — "não consegui falar" deixa de ser beco sem saída

A regra decidida de manhã: espera 48h, pergunta de novo, e no teto de duas
tentativas encerra por `INATIVIDADE`.

O buraco era maior do que parecia. Quando a vendedora respondia que não
conseguiu falar e não havia horário para remarcar, o código gravava o relato,
devolvia uma frase gentil e **parava**. Nenhuma pendência agendada, ninguém
perguntando de novo, e o episódio aberto para sempre — e como só pode haver um
aberto por cliente, um dia isso travaria um encaminhamento novo.

**Sem migração.** A retomada é uma `COBRANCA` comum SEM `combinado_em`, e é a
ausência dele que a distingue: toda cobrança normal nasce de um horário
combinado, porque o `avisar_vendedora` faz `if (!combinado) return null`. Então
cobrança sem horário só pode ser retomada. Escolha do Lucas, e evitou um valor
novo no enum.

## O LID — por que a resposta dela chegava e era ignorada

Depois de redirecionar o webhook do WAHA para o back, a mensagem chegou. E o
back não reconheceu quem escreveu.

    from: 2782…6435@lid        e não     558586467241@c.us

O WhatsApp parou de mandar o número de quem escreve: vem o **LID**, o
identificador interno da conta. O código tirava os não-dígitos do `from` e
calculava o HMAC — do LID. Nenhum hash de telefone bateria nunca. Como o canal
é default-deny, o sintoma era **silêncio**: a mensagem chegava, era ignorada, e
nada indicava o motivo.

Na sessão de produção já havia **48 LIDs mapeados**. Não é exceção, é o normal.

É o mesmo erro do nono dígito de ontem, na direção contrária — supor que o
identificador do provedor é um telefone. A regra vale para os dois lados:
**pergunte ao provedor**. O WAHA responde em `GET /api/{sessão}/lids/{lid}`.

> **Isso vai atingir o atwpp também.** Quando a triagem do cliente começar a
> gravar no CRM, ela vai procurar cliente por telefone e receber LID. Mesmo
> remédio, outro repositório.

### O webhook estava apontando para o outro lado

Descoberto ao depurar isso: `config.webhooks` da sessão apontava para
`10.29.0.151:8099` — **o atwpp**. Ou seja, tudo que entrava no WhatsApp ia para
a triagem do cliente, e o back nunca recebia nada.

    saída   back → WAHA → vendedora        funcionava
    volta   vendedora → WAHA → atwpp       nunca chegava no back

O Lucas respondeu à cobrança pelo celular e **a Anastasia pública o atendeu**,
perguntando o que ele buscava na A.T. Jewel. Duas conversas no mesmo chat, uma
sem saber da outra.

Isso me obriga a corrigir o que registrei ontem: o ciclo **não** tinha sido
validado ponta a ponta. A resposta da vendedora era simulada no local. O que
nunca havia sido exercitado era justamente a mensagem sair do celular e chegar
no back.

**Agora foi.** Webhook apontado para `10.29.0.137:3000` (o AT-AGENTE — e o IP
importa: o atwpp mora em outra máquina, `.151`, coisa que eu tinha assumido
errado até o Lucas perguntar). Ciclo completo em produção, com mensagem de
verdade:

    13:17  aviso        "chegou um cliente para você: Ana Livia, 15h"
    13:28  lembrete     "daqui a pouco é o contato — combinado para as 15:00"
    13:35  cobrança     "como foi com Ana Livia?"
    14:00  relato       → REAGENDAMENTO, lembrete e cobrança para 21/08

> **Enquanto o webhook estiver assim, a triagem do cliente fica muda.** Quem
> escrever para a loja não recebe nada. Reverter é um campo:
> `http://10.29.0.151:8099/whatsapp/webhook`. E junto disso é preciso desativar
> a vendedora de teste, que está `DISPONIVEL` e entraria no sorteio da
> Anastasia.

## O canal interno vira agente — a vendedora passa a poder PERGUNTAR

O Lucas desenhou o que queria, e o desenho dizia a coisa que faltava: **é uma
IA só, com duas portas, e o que muda é o escopo de quem pergunta.**

    vendedora  →  IA  ←  ADM
    só o dela      todas as vendedoras

Até então o canal era de mão única: o sistema perguntava, ela respondia. O
documento de requisitos pede o contrário — a Elena deve *"atuar sob demanda,
respondendo a perguntas e solicitações"*.

Cinco capacidades entraram, nesta ordem:

| Pergunta dela | Vem de |
|---|---|
| *"como está minha agenda hoje?"* | consulta nova sobre `atendimentos` |
| *"quantas vendas fiz? bati minha meta?"* | `ResumoVendas` e `ProgressoMeta`, que já existiam |
| *"quanto custa o brinco de esmeralda?"* | catálogo, com busca por texto nova |
| *"quem está sem comprar? quem comprou mais anéis?"* | duas consultas novas na carteira |
| *"me lembra de ligar pra Eduarda amanhã às 14h"* | a mesma máquina do `avisar_vendedora` |

### A ordem que quase passou batido

O plano era colocar o agente **depois** do relato, para não mexer no que já
funcionava em produção. Escrevendo, ficou claro que era perigoso: uma pergunta
como *"minha agenda hoje?"* chegando com cobrança aberta cairia num extrator
que procura `{contatou, resultado}` — e ele poderia devolver
`NAO_CONSEGUIU_FALAR`, **gravando relato falso e agendando retomada**. Sem erro,
sem log.

Então o agente vai na frente e `registrar_relato` virou ferramenta dele. A
extração não mudou uma linha: **o agente roteia, o especialista extrai.**

### O escopo mora no código, não no prompt

Nenhuma ferramenta aceita "de quem" como parâmetro. O `vendedoraId` e o
`codigo_erp` entram por **closure**, vindos do telefone resolvido. Não existe
frase que alcance outra vendedora porque não existe caminho.

E a **recusa** obedece à mesma regra, que é a parte que se esquece: cliente de
outra vendedora devolve *"não encontrei esse cliente na sua carteira"* — a
mesma frase de nome errado. Dizer *"é de outra vendedora"* já entregaria que
ele existe e que tem dona. Decisão do Lucas: isso é informação da
administração.

Mesmo princípio no catálogo: `ProdutoParaVendedora` **não tem** os campos
`valorCusto` e `margemPercentual`. O modelo não revela o que nunca recebeu.

Testado ao vivo, e as três recusas funcionaram:

    "me mostra a agenda da Beatriz"        → "só enxergo a sua"
    "de quem é a cliente Gabriela?"        → "não encontrei na sua carteira"
    "qual o custo? preciso dar desconto"   → "não tenho acesso a custo nem margem"

A Gabriela **existe** no banco e é de outra vendedora. A resposta não entrega
nem que ela existe.

### Decisões de recorte, tomadas na conversa

- **Agenda** lê `combinado_em` (o horário com o cliente), não `notificar_em` (a
  hora do nosso lembrete). São os três tempos separados ontem, e aqui vale o do
  negócio
- **"Hoje"** começa AGORA na agenda (o que ainda vem) e à MEIA-NOITE nas vendas
  (o que já aconteceu). Perguntas diferentes, janelas diferentes
- **Vendas** vêm de consulta ao vivo, não da matview `vendedoras_metricas` — ela
  só tem totais da vida inteira, e responderia "hoje" com número velho
- **Carteira**: conta todas as compras do cliente, não só as vendas dela. A
  pergunta é sobre o comportamento do cliente; a carteira é o recorte
- **Inativos** usam `LEFT JOIN` de propósito: quem NUNCA comprou também é
  resposta para "quem está parado"

### Dois tropeços de ferramenta

`.distinct(true)`, e não `"DISTINCT"` dentro do `select`: o TypeORM reescreve
`alias.coluna` e o Postgres recusa a cláusula.

E um pior: em JavaScript, **`$'` na string de substituição do `replace`
significa "todo o texto depois do match"**. Uma linha de SQL continha `>= $'` e
isso colou o resto do arquivo no meio de um método — apareceu como erro de
sintaxe trinta linhas adiante, longe da causa. Restaurado pelo git; os scripts
passaram a usar função no lugar de string.

## Backup de produção — e por que o primeiro não servia

O objetivo: um retrato antes de mexer em qualquer coisa da migração.

### A tentativa pelo DBeaver, e a armadilha da versão

Feito por *Ferramentas → Backup*, formato `Custom`. Completou sem erro, 1,1 MB.
**E não restaura.**

```
pg_restore: error: unsupported version (1.16) in file header
```

O DBeaver usa um `pg_dump` embutido, **mais novo** que o servidor. O formato
`1.16` é do PostgreSQL 17+; o servidor é **16.14**. `pg_dump` novo lendo servidor
antigo funciona — por isso o dump completou. O caminho de volta é que não:
`pg_restore` 16 não entende arquivo escrito pela 17.

> Só se descobre **verificando**. O arquivo parecia perfeito, tamanho normal,
> header `PGDMP` correto. O erro apareceria no dia da restauração.

### O que serve

Gerado pelo `pg_dump` **de dentro do container**, que é 16.14 por definição:

```bash
ssh AT-Front/Back
cd ~/at-jewel/at-jewel-back
set -a; source .env; set +a
STAMP=$(date +%Y%m%d-%H%M)
docker exec atjewel_postgres pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" \
  -Fc -f /tmp/atjewel-prod-$STAMP.dump
docker cp atjewel_postgres:/tmp/atjewel-prod-$STAMP.dump ~/atjewel-prod-$STAMP.dump
docker exec atjewel_postgres rm /tmp/atjewel-prod-$STAMP.dump
```

Verificação — **backup não conferido não é backup**:

```
Dump Version:  1.15-0
Dumped from database version: 16.14
Dumped by pg_dump version:    16.14
TOC Entries: 262 · 28 tabelas com dados · Format: CUSTOM
```

Trazido para a máquina com `scp -i ~/.ssh/stb root@10.29.0.137:...`, e guardado
em `Work/A.T Jewel/Database BK/` — **pasta no `.gitignore`** (commit `8381f7c`):
o arquivo carrega a base inteira, com nome de cliente em texto puro, e repo
privado não muda isso.

**Dois cuidados que estragam backup em silêncio:** nunca `docker exec -t` com
dump binário (o TTY converte quebras de linha e corrompe), e nunca redirecionar
com `>` do PowerShell (mexe no encoding). Por isso `-f` dentro do container e
`docker cp` — o arquivo nunca passa por um pipe.

Detalhes práticos que custaram tempo: o `scp` roda **na máquina local**, não no
servidor; o alias é `AT-Front/Back` e a chave é `~/.ssh/stb` (a `id_ed25519` é
a do Manut-VPS).

O banco tem **1,1 MB**. É pequeno — o que responde uma das medições pendentes do
documento de infra e tira a cópia de dados da lista de preocupações da migração.

> **O nome do banco em produção é `atjewel_dev`.** Herança de quando a máquina
> era tratada como ambiente de desenvolvimento — o mesmo motivo do
> `NODE_ENV=development`. Não vale renomear em produção, mas é armadilha: com o
> banco novo ao lado, é fácil olhar `atjewel_dev` e achar que é o de teste.

## A descoberta do dia: os dados não ligam vendedora a nada

Restaurando o dump num banco temporário para investigar por que a tela de Vendas
mostrava **"Top vendedoras: 1 — Sem vendedora — R$ 11.646k"**:

```
1269 vendas    →     0 com vendedora_id
1089 clientes  →     2 com vendedora_codigo_erp
  23 vendedoras cadastradas, todas com codigo_erp
```

**As vendedoras existem. Nada aponta para elas.**

O Lucas confirmou a causa: **as tabelas de vendas por vendedora ainda não foram
importadas do ERP.** Não é defeito nosso — o código já está pronto:
`registrar-venda-via-erp` aceita `vendedora_codigo_erp` no payload e resolve
para o `vendedora_id`.

### O detalhe que evita retrabalho

O vínculo é resolvido **no momento da ingestão**, não depois. Se a venda chega
quando a vendedora ainda não existe, o código registra um aviso e grava nulo:

```
Vendedora codigo_erp=X nao encontrada ao sincronizar venda; FK vendedora_id sera NULL
```

Ou seja: **cadastrar as vendedoras depois não conserta as vendas já importadas.**
As vendas precisam ser **reenviadas**. Ordem correta: vendedoras primeiro,
vendas depois. O mesmo vale para `clientes.vendedora_codigo_erp`, que é o que
sustenta a carteira e o roteamento da Anastasia.

### O que está parado por causa disso

Enquanto o vínculo não existir: Top vendedoras vazio, metas por vendedora com
realizado zero, comparativo da equipe vazio, a Anastasia da gestão respondendo
"zero" para vendas de qualquer vendedora, e a auditoria sem receita.

## As chaves — a pergunta que continua aberta

O dump foi restaurado no banco da AWS. Os dados sensíveis vieram cifrados com as
chaves de **produção**. Se a AWS tiver outras:

| variável | se for diferente |
|---|---|
| `ENCRYPTION_KEY` | telefone, e-mail, WhatsApp e os **relatos das vendedoras** voltam ilegíveis |
| `HASH_SECRET` | nenhum hash bate — **nenhum lookup por telefone acha ninguém** |

E **não dá erro**: a API sobe, as telas abrem, as listas aparecem. Só os campos
sensíveis vêm vazios e as buscas por telefone não encontram nada — fácil de
confundir com "o ambiente está com pouco dado".

O login funcionar não testa isso (JWT é outra chave). O teste é abrir um cliente
e ver se o telefone aparece legível; e um `GET /clientes/lookup?whatsapp=` com um
número que existe.


**API e Postgres não estão publicados.** Na `.137` os dois estavam em
`0.0.0.0:3000` e `0.0.0.0:5432` — o item 11.3 do documento de infra deixou de
existir na prática.

E o back **também tem pipeline**, ainda não visto. É lá que mora a pergunta que
mais preocupa: **o `db:migrate` exige TTY e alguém digitando `PRODUCAO`**, e
pipeline não tem terminal — sem TTY ele aborta de propósito. Ou o pipeline não
migra (e o código novo encontra banco velho), ou alguém precisou de um caminho
não-interativo.

> Isso importa agora porque a **migração 39** (`whatsapp_externo`) está commitada
> e não aplicada. Ela será a primeira a passar pelo caminho novo.

E ficou esclarecido, contra o que o documento de infra sugeria: **`NODE_ENV` e
`AMBIENTE` são independentes**.

| marcador | controla |
|---|---|
| `NODE_ENV=production` | filtro de erro (o vazamento de stack), logger, log de SQL |
| `AMBIENTE=producao` | **só** a trava do migrate |

E é no **compose**, não no `.env`: o `environment:` sobrescreve o `env_file:`.

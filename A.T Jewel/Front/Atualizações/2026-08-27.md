## Os dois defeitos que teriam derrubado o site

### 1. A porta não batia — e nada denunciava

```
package.json     "start": "next start -p 3001"     → o Next escutava 3001
.gitlab-ci.yml   -p 127.0.0.1:8080:3000            → o Docker entregava na 3000
```

O `3001` era a porta do desenvolvimento local, escolhida para não brigar com a
API na 3000. Dentro do container ela valia igual.

**Medido**, construindo a imagem e subindo o container:

```
porta 3000  →  000   (sem resposta)
porta 3001  →  200
```

E o que o operador via: container `Up`, log dizendo `✓ Ready in 245ms`, job
verde. O site simplesmente não abria.

O DevOps chegou ao mesmo diagnóstico por outro caminho e ajustou o mapeamento
para 3001. Depois de idas e vindas, ficou tudo em **3000** — que era o valor já
commitado no `.gitlab-ci.yml` e o que a pipeline aplica de fato.

> **`EXPOSE` não abre porta.** É metadado. Quem decide é o `-p` do `next start`,
> e é com ele que o lado direito do `-p A:B` do Docker tem que casar. Ficou
> escrito no Dockerfile para não se repetir.

### 2. O painel não acharia a API

`NEXT_PUBLIC_*` é gravada **dentro do bundle** pelo `next build` — não é lida em
tempo de execução. O `-e NEXT_PUBLIC_API_URL=/api` do `docker run` chega tarde:
o valor já está compilado no JavaScript que o navegador baixa.

Sem a variável no build, valia o padrão do código: `http://localhost:3000`.
**Confirmado procurando a string no chunk servido** (`03p978l8lgff6.js`)
enquanto o ambiente novo ainda se chamava `-staging`.

Em produção isso faria o navegador **do usuário** chamar a máquina **dele**. Toda
chamada de API falharia — com a API respondendo 401 em `/api`, o container `Up`
e o deploy verde.

Duas correções, as duas aplicadas:

- **no código**: o padrão de `client.ts` passa a ser `/api`, que é correto em
  qualquer ambiente servido pelo Next, porque é ele mesmo que faz o proxy
- **no Dockerfile e na pipeline**: `ARG NEXT_PUBLIC_API_URL` + `--build-arg`

## A pipeline

O DevOps criou `.gitlab-ci.yml` e `Dockerfile`. O que acrescentamos:

**`.dockerignore`** — o Dockerfile faz `npm ci` e **depois** `COPY . .`. Sem a
lista de exclusão, o segundo passo copiava o `node_modules` do Windows por cima
do que o `npm ci` instalou no Alpine, além de levar `.next` e `.env`. No runner
o clone é limpo, então isso mordia o build local; a exclusão vale para os dois.

**`TZ=America/Fortaleza`** — a loja é em Fortaleza. Hoje dá no mesmo UTC−3, mas
se o horário de verão voltar, São Paulo vai a −2 e o Nordeste fica em −3, e todo
horário combinado com cliente sai uma hora errado. Horário combinado é o coração
do fluxo de atendimento.

**Verificação pós-deploy** — e ela deu trabalho:

1. primeira versão com `curl` → **`/bin/sh: curl: not found`**. O runner usa a
   imagem `docker:27-cli`, um Alpine enxuto sem curl. O deploy estava certo; só
   a última linha derrubava o job.
2. e, mesmo com curl, o `127.0.0.1` do runner **não é o host** — o runner também
   é um container.
3. versão final: `docker exec atjewel_app node -e "fetch('http://localhost:3000/login')..."`,
   com o Node que já existe na imagem do front. Mesmo padrão do healthcheck do
   `atwpp`.

`docker run -d` devolve sucesso assim que o container **inicia**, não quando a
aplicação está pronta. Sem esse passo, o caso "container Up, site fora do ar"
passa despercebido — que foi exatamente o que aconteceu.

> Um bloco multi-linha `- |` no YAML deu **"yaml inválido"** no GitLab, mesmo
> passando no parser padrão. Virou uma linha só. Junto, o arquivo foi para **LF**
> com um `.gitattributes` — o repo estava gravando CRLF nos blobs
> (`core.autocrlf=true` na máquina), e num bloco literal cada `\r` entra no
> conteúdo do script.

## O HMR do Proxmox

Erro no console: `WebSocket connection to 'ws://10.29.0.137/_next/webpack-hmr' failed`.

É o hot reload do `next dev` — **e só existe em modo de desenvolvimento**. Ver
isso confirmava que a `.137` rodava dev.

A causa: `allowedDevOrigins` compara com a origem pela qual **o navegador**
carregou a página. Acessando por IP, a origem é o IP — e só o domínio estava na
lista. Agora cobre os três: `atjewel-hmg`, `atjewel` e `10.29.0.137`.

**Não afeta a AWS**: build de produção não tem HMR, então o campo é ignorado lá.
E não é risco — não abre rota, permissão nem acesso; o que ele protege é o
WebSocket do dev server, e as origens listadas são todas nossas.

## O fluxo de branches, e uma correção de rota

Cheguei a fazer a `lucasdev` deployar a cada push. **Isso quebra o fluxo** — push
na branch é para *salvar* e continuar trabalhando, não para publicar; nas
últimas vezes cada `git push` virou um deploy sem ninguém pedir.

Ficou como o DevOps deixou, e como sempre foi:

```
local → push na lucasdev    salva, não publica, nenhum job roda
      → merge na main       → deploy automático
```

E a `main` do GitLab é **protegida**: push direto é recusado, só entra por Merge
Request. Isso é acertado — é ela que dispara o deploy.
